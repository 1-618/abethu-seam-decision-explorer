Architecture record, pre-ADR-010

One product, two clouds,
and the seam between them.

The frontend is now definitively split: the public website is Next.js on Vercel (cpt1, Cape Town) and the LMS is TanStack Start on AWS (af-south-1, Cape Town), with Directus writing the cms schema beside the operational public schema in one VPC-private RDS PostgreSQL 16. Same city. Different clouds. Every interesting problem in this document lives in the amber band between the two dashed boxes below.

This page exists so the six seam decisions — A through F — get made deliberately, with the trade-offs on the table. Each decision carries one interactive diagram per option: every box opens a full breakdown with code, every arrow reports what travels along it, and the recommended options step through as a walkthrough. Beneath each diagram sit latency, freshness, complexity, PII placement and failure modes, then a recommendation. The decision sheet at the end assembles the picks into the sign-off string and an ADR-010 draft.

The problem

Why the seam is the whole design

ADR-005 makes RDS VPC-private — nothing outside the VPC connects to it directly. Vercel functions, even running in cpt1 a few kilometres from af-south-1, are outside that VPC. So the pattern the wireframes and the exploration doc assumed — "the site reads cms and public directly over pg" — cannot exist as written. Every one of the six decisions is a consequence of that single fact.

The connection math

An RDS t4g.small defaults to roughly 190 connections, a limit derived from instance memory. Vercel scales function instances with traffic — a campaign burst can mean hundreds of concurrent instances, and with direct pg each one wants a connection of its own. The LMS, meanwhile, holds a long-lived pool shared by its request handlers and pg-boss workers. Two connection models against one small database — resolved by giving the site zero connections.

The PII line

Marketing copy is not personal data — it can live anywhere. Lead PII (name, phone, email in inquiries) is, and POPIA is the reason af-south-1 was chosen at all. The write path decision (C) is really the question: whose memory does the PII pass through, and where does it rest? The recommended shape stores it only in-VPC.

Two deploy models

Vercel is git-push with preview deploys per PR; AWS is CDK + GitHub Actions OIDC (ADR-007). That's two environment matrices, two secret stores, two monitoring surfaces. Preview deploys also need a data story — a staging seam API or fixtures — or every PR preview hits production facts.

Two origins, one product

abethuskills.co.za (Vercel) and app.abethuskills.co.za (AWS) are different origins. Cookies, sessions and CSRF all care about that boundary — decision D chooses whether a session ever exists on the marketing origin. The printed certificate QR (decision E) chooses which origin goes on paper, permanently.

What survives untouched: the v4.17 schema already encodes the boundary — three schemas, Directus role scoped to cms+directus, public structurally unreachable from the CMS. The split changes transport, never semantics.

Interactions

Cross-couplings

The six decisions are not independent. These are the edges between them:

B4 collapses B into A

If facts are pushed into cms, the "live facts" read path becomes the content path — and the ops/marketing schema boundary you drew on purpose starts to blur. Choosing B4 makes decision F mostly moot too, because freshness stops being a caching question and becomes whatever the job cadence is.

B5 breaks the JSON-LD

Client-side facts never enter the HTML, so the Course JSON-LD ships without a price and SERP ↔ page parity dies — Google sees one thing, the visitor another. B5 is only acceptable as a live widget on top of B3, never instead of it.

C4 breaks the v4.8 echo

The idempotency contract returns the existing row on a duplicate (23505 → same-row echo). A queue makes the write async — the form can only say "accepted", not "here's your enquiry". The database guarantee survives; the UX contract doesn't.

F3/F4 presuppose pg-boss

Event-driven revalidation needs the job plumbing that also serves B4. Start on F2; graduate to F4 when pg-boss exists for other reasons — don't build the event bus for freshness alone.

Accepted overhead

Second-order costs of the split

These hold whichever letters are picked:

The seam contract

The LMS read API + inquiries endpoint is a versioned public contract: rate limits, server-to-server auth, and bot defence (Turnstile / honeypot — the idempotency key dedups retries, not abuse). Recommend a shared seam-contract package (zod schemas) as the single source of payload truth.

Shared design system

App Router and TanStack Router can't share shells. Tokens and primitives (Button, Badge, Card, Table) move into a router-agnostic @abethu/ui package — which argues for a pnpm/Turborepo monorepo: site · lms · ui · seam-contract.

Attribution across the seam

The "ad → lead → enrolment → invoice in one query" goal only survives if UTM/source fields captured on Vercel ride inside the inquiries payload into public.inquiries. One forgotten field breaks the profitability chain at the seam.

Docs to correct

Invariants

What doesn't change

The schema layer is untouched: all 67 public tables, the 7 cms tables, the replay pipeline, the probes, and the Directus role scoping stand exactly as encoded in v4.17. The 13 integration touchpoints keep their semantics — who writes what, which views feed which surfaces — and change only their transport. G2 (online payments) remains the sole schema-complete gate, and none of A–F touches it.
